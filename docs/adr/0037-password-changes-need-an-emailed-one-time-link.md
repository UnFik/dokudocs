# Setting or changing a password needs a one-time link sent to the account email

A signed-in User sets or changes the password only by presenting a link mailed to the account email: `POST /auth/password/link` sends it, `POST /auth/password/check` says whether it is still usable without using it up, and `POST /auth/password` takes `{ token, password }` and replaces the hash. The link is one per User (a new one replaces the old), works once, expires in an hour, can be asked for once a minute, and works only for the User it was made for; every failure answers the same way. Only its hash is stored, in `password_tokens`. The old `POST /auth/password`, which set a password from a bearer token alone, is gone. A successful change mails the account email a notice with no link. The endpoints sit behind the unverified-email gate of [ADR-0035](0035-unverified-email-is-a-hard-gate-carried-in-the-jwt.md).

The reason is that a bearer token proves a session, not the mailbox: whoever holds a stolen token could add a password and keep the account after the token expires. The link proves control of the mailbox at the moment of the change, and the notice is the only signal the owner gets if it was not them. No current password is asked for, because the mailbox is the proof and a Google-only User has no current password to give. Issued JWTs cannot be revoked ([ADR-0034](0034-oauth-identities-link-by-provider-subject.md)), so other sessions stay valid after a change until they expire.

Rejected: keeping the direct endpoint (a leaked token becomes a permanent takeover), asking for the current password (does not fit a User who has none), and reusing `email_verifications` with a purpose column (the two links differ in lifetime and in being bound to a User, and sharing a table would couple their cleanup). `password_tokens` is built so a later "forgot password" without sign-in can reuse it.
