# Serialize access changes with document writes

Each durable document write rechecks effective access in one transaction using this lock order: shared workspace membership, all involved project rows in ascending project UUID order, project membership rows in the same order, document row `FOR UPDATE`, then shared direct document grant. When an operation depends on more than one workspace member (for example, granting access to another user), lock all required membership rows in ascending user UUID order before project locks. When a direct grant row does not exist, the document row is its parent fence. Access mutations take exclusive locks on the same source rows in the same order: workspace membership changes lock affected membership rows in ascending user UUID order; project membership, visibility, and category changes lock workspace membership first, then the project row `FOR UPDATE`, then project membership; document grant and lifecycle changes follow the document path. Workspace deletion locks all workspace membership rows in user UUID order before deleting the workspace and its cascaded data. A revoke that commits first blocks the next write; a write that gets the locks first commits before the revoke. Project placement into a private project additionally requires target project manager/editor or workspace owner/admin; a direct document edit grant alone does not authorize placement. This also serializes body writes with document visibility and lifecycle changes without locking every document affected by a workspace or project change.
